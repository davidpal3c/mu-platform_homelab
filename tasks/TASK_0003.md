# TASK-0003 — k3s Cluster Bootstrap (Phase 0C)

**Status:** Ready  
**Phase:** 0 — Platform Foundation / **0C — Kubernetes Platform Bootstrap**  
**Dependencies:** TASK-0002 complete and verified

---

## Objective

Install and stabilize a single-node k3s control plane on `aluna-node-01` while preserving storage-tier separation established in Phase 0B.

---

## Why now

Phase 0A and 0B are complete. The node has:

- RAID1 boot tier in service (`/boot`, `/`, `/var`)
- `/platform`, `/data`, `/backups` mounted via UUID
- bind mounts from `/platform/*` to `/var/lib/*` high-churn runtime paths

This is the correct point to bootstrap Kubernetes without violating storage architecture principles.

---

## Scope

- Install k3s control plane on the host.
- Validate that runtime data paths used by k3s resolve to `/platform` via bind mounts.
- Configure baseline namespaces:
  - `aluna-access`
  - `aluna-context`
  - `aluna-mira`
  - `aluna-terra`
- Verify cluster readiness, networking baseline, and DNS.
- Verify default storage class and run a PVC smoke test using local-path.
- Produce an operator runbook and a build report.

---

## Naming convention decision (locked for execution)

For this task, namespace and runtime naming uses the Aluna convention:

- `aluna-access`
- `aluna-context`
- `aluna-mira`
- `aluna-terra`
- `observability`

Do not introduce new `opencontext-*` namespaces in TASK-0003.
Any legacy-name migration beyond this scope is handled by a later, explicit
naming convergence task.

---

## Non-scope

- TLS and public ingress hardening (TASK-0005)
- Observability stack deployment (TASK-0004)
- Aluna Context API or any workload deployment
- Multi-node clustering or HA control-plane design

---

## Constraints

- Do not alter boot RAID layout (`sda`/`sdc`, `md0/md1/md2`).
- Do not reformat storage tiers.
- Keep runtime churn off boot tier by honoring existing bind mounts.
- Maintain infrastructure-only focus for Phase 0.

---

## Risks

- k3s may start with incorrect runtime path assumptions if bind mounts are absent at boot.
- Single-node capacity constraints (CPU/memory/disk) may affect control-plane stability.
- Networking/firewall defaults can block API server access or pod networking.

---

## Acceptance criteria

1. `kubectl get nodes` reports node `Ready`.
2. `kubectl get pods -A` shows core system pods healthy.
3. Required namespaces exist.
4. `findmnt` confirms `/var/lib/rancher`, `/var/lib/kubelet`, `/var/lib/containerd` are backed by `/platform/*`.
5. A smoke-test PVC binds and a test pod mounts it successfully.
6. Build report and doc updates are prepared.
